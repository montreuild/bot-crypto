## 2. Constats résolus (5)

### ✅ O-02 — Le gate d'apply se prononce sur une tranche jamais vue

`auto_optimizer.py:576-600`. Un troisième découpage (`split_with_holdout`,
`app/core/is_oos.py:41`) réserve 20 % de la fin de l'historique. Le gate
rebackteste le gagnant dessus et **réaffecte effectivement** les variables :

```python
if _h:
    gate_source = "holdout"
    oos_trades      = _h.get("trades", 0)      # ← réaffectation réelle
    best_oos_pnl    = _h.get("pnl", 0)
    best_oos_wr     = _h.get("wr", 0)
    best_oos_sharpe = _h.get("sharpe", 0)
```

C'était le point à vérifier : les noms de variables sont restés `best_oos_*`,
mais les valeurs viennent bien du holdout. `gate_source` trace la provenance
et est journalisé + stocké dans la fiche de job.

Qualité du correctif, au-delà du fait qu'il marche :

- **le baseline est mesuré sur la même tranche** que le candidat
  (`auto_optimizer.py:602-603`) — sans quoi la comparaison ne voudrait rien dire ;
- **refus franc plutôt que dégradation silencieuse** : le holdout n'est réservé
  que s'il est exploitable (`min_holdout_bars`, et assez de reste pour la
  recherche), sinon `df_holdout = None`, retour à l'ancien contrat **et raison
  journalisée** (`is_oos.py:50-56`) ;
- `_cfg_avec_params` vide `optimizer_results` avant le backtest du candidat —
  sinon on mesurerait le paramétrage actuel en croyant mesurer le candidat.
  C'est le même piège que `_eval` désamorçait déjà, correctement reproduit ici.

### ✅ O-03 — Le walk-forward ne voit plus le holdout

Le paramètre de `_run_one_job` reçoit désormais `df_recherche` et non la série
complète (`auto_optimizer.py:460` et `:874`). `_wf_consistent()` opère donc sur
la partie recherche uniquement. Voir toutefois **N-03** ci-dessous sur le nom.

### ✅ O-07 — `n_trials` du Deflated Sharpe est le nombre réel

`auto_optimizer.py:624-627` :

```python
# Le nombre d'essais RÉELLEMENT tirés, pas celui demandé : c'est
# lui qui mesure le biais de sélection multiple à corriger.
_ds_n_trials = int(result.get("n_trials") or n_trials_eff) if _ds_gate_enabled else 1
```

### ✅ M-02 — Embargo entre entraînement et validation

Nouveau module `app/ml/splitting.py` (114 lignes) portant la convention pour
les **trois** entraîneurs (MLBackend, `recipe_trainer`, `ml_dynamic_threshold`)
plutôt que trois copies :

- `label_embargo(horizons)` → l'horizon **maximal** (« une seule tête qui
  regarde 12 barres devant suffit à contaminer 12 lignes ») ;
- `chrono_split` → `SplitPlan(train, split, n, embargo)` ;
- `purged_time_series_splits` pour les folds walk-forward.

Deux détails qui font la différence :

- **l'embargo ne mord que sur la fin de l'entraînement**, la validation garde
  toutes ses lignes — donc l'AUC reste calculée sur le même échantillon et les
  mesures d'avant et d'après restent comparables. C'est le bon arbitrage ;
- `train_multi` applique l'embargo **par symbole avant concaténation**, sinon
  on ne retirerait des lignes qu'au dernier de la liste. Cas particulier traité
  plutôt que contourné.

Test dédié : `tests/test_ml_splitting.py` (111 lignes), avec vérification qu'à
embargo nul le découpage est identique indice pour indice.

### ✅ O-01 — requalifié plutôt que résolu

Mon constat disait « l'objectif d'optimisation **est** le score OOS, donc il
n'y a pas d'out-of-sample ». Avec le holdout, le dispositif devient le
découpage à trois tranches que je recommandais :

```
[--- IS ---][--- sélection ---][--- holdout (20 %) ---]
  entraînement   objectif de         gate d'apply,
                 la recherche        touché une fois
```

Sélectionner sur une tranche de validation est une pratique **légitime** ; ce
qui ne l'était pas, c'est de décider dessus. `_penalized_score` lit toujours
`r["oos_score"]` (`optimizer_search.py:313-315`) et c'est désormais correct.

**Il reste un problème de nom** : la tranche de sélection s'appelle encore
`oos`, `df_oos`, `best_oos_pnl`, `oos_score`. Un lecteur qui voit
`oos_pnl` croira lire une mesure hors échantillon alors qu'elle est maximisée
sur N essais. Renommer en `val_*` coûte un `sed` et supprime une confusion
durable.

## 5. Nouveaux constats (4)

### N-01 🟠 `required_total_bars` ignore le holdout

`optimizer_search.py:143` :

```python
oos_needed = min_bars + _oos_trade_window_bars(timeframe)
return math.ceil(oos_needed / _OOS_FRACTION)          # 0.35 seulement
```

La formule dimensionne le fetch pour que la tranche OOS (35 %) contienne le
warmup plus une fenêtre de trading. Elle **n'a pas été mise à jour** pour les
20 % désormais prélevés en amont par `split_with_holdout`.

Conséquence : `auto_fetch_limit` sous-provisionne d'un facteur
`1 / (1 − 0,20) = 1,25`. La garde d'exploitabilité de `split_with_holdout`
(`is_oos.py:64-70`) se déclenche donc plus souvent que nécessaire, et le
pipeline **retombe silencieusement sur l'ancien contrat sans holdout** — c'est
exactement le cas que le correctif voulait éviter. Le repli est journalisé
(`auto_optimizer.py:274-281`), mais en INFO, sur une condition que personne ne
surveille.

Ce sont surtout les stratégies à gros warmup (les familles `opus_omnibus_v*`,
justement celles que le commentaire de `required_total_bars` cite comme motif
d'origine de la formule) qui perdront leur holdout.

**Correction** :

```python
from app.core.is_oos import HOLDOUT_FRACTION_DEFAULT as _HOLDOUT
return math.ceil(oos_needed / (_OOS_FRACTION * (1.0 - _HOLDOUT)))
```

et journaliser en WARNING, pas en INFO, quand un holdout est refusé.

### N-02 🟠 Le bouton « Appliquer » de l'UI décide encore sur la tranche de sélection

`app/api/routes/optimizer.py:342-350` :

```python
ok_quality, reason = beats_baseline(
    result.get("best_oos_trades", 0), result.get("best_oos_pnl", 0),
    result.get("best_oos_wr", 0), result.get("best_oos_sharpe", 0),
    job.get("baseline", {}), …)
```

Ces quatre valeurs viennent de `result`, c'est-à-dire de la **tranche de
sélection**. Or `auto_optimizer` stocke déjà le résultat du holdout dans la
fiche de job (`_update_job(job_id, holdout=_h, gate_source="holdout")`,
ligne 591) : **la donnée est disponible et n'est pas lue.**

Le résultat est une asymétrie inconfortable :

| Chemin | Tranche du gate |
|---|---|
| auto-apply (`auto_apply=True`) | **holdout** ✅ |
| bouton « Appliquer » de l'UI | **sélection** ❌ |

Et c'est le chemin manuel que l'utilisateur emprunte le plus souvent —
`auto_apply` est désactivé par défaut. Le correctif porte donc sur le chemin
qui sert le moins.

L'intention de mutualisation était bonne : `beats_baseline` est bien une
fonction pure partagée. Mais partager la **fonction** ne suffit pas si les deux
appelants lui passent des **fenêtres** différentes.

**Correction** :

```python
_h = job.get("holdout") or {}
ok_quality, reason = beats_baseline(
    _h.get("trades", result.get("best_oos_trades", 0)),
    _h.get("pnl",    result.get("best_oos_pnl", 0)),
    _h.get("wr",     result.get("best_oos_wr", 0)),
    _h.get("sharpe", result.get("best_oos_sharpe", 0)),
    job.get("baseline", {}), …)
```

et renvoyer `gate_source` dans la réponse pour que l'UI puisse l'afficher.

### N-03 🟡 Le paramètre `df_full` ne contient plus la série complète

`auto_optimizer.py:474` : la signature de `_run_one_job` déclare toujours
`df_full: pl.DataFrame = None`, et les deux appelants (lignes 460 et 874) lui
passent `df_recherche`. À l'intérieur, `_wf_consistent()` lit `df_full` et sa
docstring dit encore « si les données **complètes** manquent ».

Fonctionnellement correct — c'est bien ce qu'on veut que le walk-forward voie.
Mais c'est précisément le motif que je relevais en **X-07** : un identifiant et
un commentaire qui décrivent un état qui n'est plus vrai. Ici il vient d'être
recréé.

**Correction** : renommer le paramètre `df_recherche` et ajuster la docstring.

### N-04 🟠 `exit_mode` n'existe qu'en backtest

`app/core/execution.py:155` introduit `apply_exit_mode(signal, mode, params)`
avec quatre modes nommés (`sl_tp`, `trailing`, `trailing_after_profit`,
`tp1_tp2_runner`). L'intention est excellente et répond à un vrai problème,
énoncé dans le commit : « comparer deux stratégies revenait à comparer AUSSI
deux gestions de position, sans pouvoir dire laquelle expliquait l'écart — le
dossier `smc_ml_edge` a buté exactement là-dessus, le coupable étant un stop
trop serré et non le signal. »

Recensement exhaustif des appelants :

```
app/engine/backtest.py:18     import
app/engine/backtest.py:1076   appel
tests/test_exit_modes.py      10 appels
```

**Zéro occurrence de `exit_mode` dans tout `app/live/`.**

Donc `backtest.exit_mode: tp1_tp2_runner` dans la config change la gestion de
sortie du backtest, et le live continue en `as_declared`. Un paramétrage validé
sous un mode de sortie serait tradé sous un autre.

Le placement de la fonction dans `app/core/execution.py` — le module dont la
docstring dit « source unique des formules monétaires, consommée par
`app/engine/backtest.py` **ET** `app/live/position_*_mixin.py` » — rend la
chose particulièrement piégeuse : elle *ressemble* à du code partagé.

Atténuation : `exit_mode` vaut `as_declared` par défaut, donc le comportement
actuel est identique des deux côtés **tant que personne n'y touche**. Le risque
se matérialise au premier usage de la fonctionnalité.

**Correction** : appeler `apply_exit_mode` dans `_try_open_from_signal`
(`position_open_mixin.py`) juste avant `_open_position`, avec la même
résolution de priorité (`signal["exit_mode"]` puis config). Et ajouter le mode
au test de parité `test_backtest_live_parity.py`.

## 7. Remarque de méthode

Trois jours d'écart ont suffi à périmer une partie de cet audit. Deux
enseignements :

1. **Un audit doit dire sur quel commit il porte.** L'audit initial ne le
   disait pas — il datait la journée, pas la base. Cette révision porte
   `32d6c90` en tête, et les futures devraient faire de même.
2. **Les correctifs de cette semaine ont trouvé deux bugs que je n'ai pas
   vus** (`b791e40`, `b25cb56`), tous deux dans des fichiers que j'avais lus.
   Ma revue a vérifié les invariants là où le code les **énonce**, pas chez
   chacun de leurs **consommateurs** : `backend/trainer.py` documentait
   `bt_train_offset`, et je n'ai pas vérifié que v4/v5 l'honoraient. C'est le
   type d'écart qu'un test de propriété attrape et qu'une relecture manque —
   ce qui renforce T-04 plutôt que de l'affaiblir.
